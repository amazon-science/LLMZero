# Task: LoRA (rank=alpha=64) GRPO post-training of Qwen3-4B on SSMR-Bench (music-theory multiple-choice), maximizing validation accuracy (val-core/ssmr_agg__dev). Starting point is a TUNED LoRA GRPO baseline (high LoRA learning rate + long response budget); the search tunes the RL/optimization hyperparameters from there.

Framework: verl_grpo (verl 0.9.0 GRPO via `python3 -m verl.trainer.main_ppo`). Compute: slurmdocker, 1 node x 8 GPUs, <slurm_partition>, verl container (docker/llmzero-verl-0.9.0.sqsh).
This is LoRA reinforcement fine-tuning with a rule-based reward (exact-match on a boxed letter). Rollouts are generated with vLLM; only the LoRA adapter is updated with GRPO advantages; the base weights are frozen.

## Baseline = a TUNED LoRA GRPO recipe (NOT verl defaults)
The Reference Bash Script below is the STARTING point. Unlike a raw-default baseline, it sets a LoRA-appropriate learning rate and a response-length budget large enough to avoid answer truncation, because the verl DEFAULTS are wrong for this task:
  - `actor_rollout_ref.actor.optim.lr=5e-5` — verl's default `lr=1e-6` is a FULL-FINETUNE learning rate; a LoRA adapter updates only a small fraction of params and needs a substantially higher learning rate. A prior search that kept lr near the verl default produced a frozen adapter that never beat the base model. lr is the primary lever; see "Fixed vs Tunable".
  - `data.max_response_length=8192` — verl's default truncates. With thinking enabled, a large fraction of rollouts hit the cap and the trailing `\boxed{X}` answer is cut off (data.truncation=right), zeroing the reward on correct-but-truncated responses. 8192 gives the `<think>` trace + boxed answer room. Do NOT use `thinking_budget` to bound thinking; give the response length room instead.
  - `data.max_prompt_length=4096` — generous headroom for the prompt (verl default 512 would truncate the longest prompts).
  - `algorithm.adv_estimator=grpo` (verl's raw default is `gae`, which needs a critic; GRPO is the algorithm for this task).
  - `actor_rollout_ref.rollout.n=8` (group size for GRPO advantage; verl default 1 gives no group baseline).
  - LoRA is ENABLED and FIXED: `actor_rollout_ref.model.lora_rank=64`, `actor_rollout_ref.model.lora_alpha=64`, `actor_rollout_ref.model.target_modules=all-linear`. LoRA requires `actor_rollout_ref.rollout.load_format=safetensors` and `actor_rollout_ref.rollout.layered_summon=true` (vLLM adapter sync + sharded param gather).
  - the reward function, data paths, model path, thinking-enabled chat template, and checkpoint save/load contents.
Everything else (KL coefficient, entropy coefficient, clip ratios, batch sizes, mini-batch, warmup, rollout group size, run length) starts at the Reference values below and is TUNED by the proposer to improve val accuracy.

## LoRA shape is LOCKED (do NOT tune rank/alpha)
`actor_rollout_ref.model.lora_rank=64` and `actor_rollout_ref.model.lora_alpha=64` are FIXED for the whole search and MUST stay identical on every node. Reason: checkpointing is ENABLED (see below) and warm-started child nodes resume the parent's LoRA adapter — the adapter tensor shapes must match the checkpoint being loaded, or the resume fails. Tune the optimization/RL hyperparameters (learning rate, KL, entropy, clip, batch sizes, rollout.n, warmup, run length) instead. The proposer must NOT propose changes to lora_rank, lora_alpha, or target_modules.

## Checkpointing: ENABLED (LoRA-adapter warm-start / deepening)
checkpoint_optimization is ENABLED. The MCTS mixes from-scratch root nodes with warm-started children that resume a parent's trained LoRA adapter and train additional steps.
- SAVE (every node): `actor_rollout_ref.actor.checkpoint.save_contents=["model","optimizer","extra"]` + `+actor_rollout_ref.actor.checkpoint.save_lora_only=True`. On a LoRA model verl 0.9.0 writes a COMPACT LoRA-only FSDP-sharded checkpoint (`actor/model_world_size_*_rank_*.pt`, ~tens of MiB/rank) — NOT a fused full model.
- RESUME (warm-started children only): when a "RESUME FROM CHECKPOINT" block is present, follow it EXACTLY — it sets `trainer.resume_mode=resume_path`, `trainer.resume_from_path=<parent>/global_step_N`, `actor_rollout_ref.actor.checkpoint.load_contents=["model"]` (weights/adapter ONLY, fresh optimizer so the proposer's LR changes take effect), the `rm -f .../data.pt` line, and the `total_training_steps` step cap. verl auto-detects the LoRA-only state dict and loads it (`strict=False`); resume_from_path also inherits the parent's global step.
- Do NOT set `actor_rollout_ref.model.lora_adapter_path` — that key loads an externally-provided PEFT adapter directory, which training does NOT produce; the sharded `["model"]` resume above is the correct path.
Run length per node is controlled by `trainer.total_training_steps` (bounded by the checkpoint block / max_steps_per_node), NOT by epoch count. This LoRA save/load round-trip is verified on this verl 0.9.0 image (compact LoRA-only shards; resume logs "Loaded LoRA-only checkpoint (N keys)").

DATA PATHS ARE CONCRETE AND FIXED — use them EXACTLY as written. Shared by every node:

## verl 0.9.0 schema notes (IMPORTANT — differ from older verl)
- The thinking toggle is `+data.apply_chat_template_kwargs.enable_thinking=True` (the key `apply_chat_template_kwargs` is an EMPTY struct by default, so the leaf MUST be added with a `+` prefix; the old `data.chat_template_kwargs...` key does NOT exist in 0.9.0).
- verl 0.9.0 requires `actor_rollout_ref.ref.log_prob_micro_batch_size_per_gpu` AND `actor_rollout_ref.rollout.log_prob_micro_batch_size_per_gpu` to be set explicitly (it errors if neither the batched nor per-gpu form is given).
- **Custom reward keys live under `reward.*` in verl 0.9.0.** Use `reward.reward_manager.name=naive` and `reward.custom_reward_function.{name,path}` — NOT the old top-level `reward_model.reward_manager` / `custom_reward_function.*` (those are 0.7.1-era; with them, verl's async reward-loop falls back to the built-in `default_compute_score` registry and raises `NotImplementedError: Reward function is not implemented for data_source='ssmr_...'`).
- Do NOT set `actor_rollout_ref.rollout.mode` — the default (`async`) is correct in 0.9.0; leave it unset.
- LoRA: `actor_rollout_ref.rollout.load_format=safetensors` is REQUIRED (vLLM loads the base in a LoRA-compatible way); `actor_rollout_ref.rollout.layered_summon=true` avoids gathering the full FSDP param set at once when syncing the adapter to vLLM.

## Dataset notes
SSMR-Bench is a music-theory multiple-choice benchmark (beat / chord / interval / scale). Each `prompt` is a system+user chat: the system instructs the model to reason and output a single letter A/B/C/D inside `\boxed{X}`; the user gives ABC-notation context and four options. The reward (compute_score) strips `<think>...</think>`, extracts the last `\boxed{X}`, and returns 1.0 if the letter matches ground truth else 0.0.
- Train: 5000 rows, per-category data_source. Val: 500 rows, unified `ssmr_agg__dev`. Test: 500 rows, per-category.
- Prompts are SHORT (max ~730 tokens); the length budget is entirely for the response (thinking + boxed answer).
- Baseline reference accuracy: Qwen3-4B ~50.8% (measured with a bounded thinking budget). Random 25%. NOTE: the untruncated base greedy val here is ~0.37 BECAUSE of response truncation at 4096 with unbounded thinking — this description fixes that via max_response_length=8192, so a correctly-configured base should score higher than 0.37.
